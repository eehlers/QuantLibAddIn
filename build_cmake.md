# Build the whole stack from a git clone using cmake

This document explains how to build the entire QuantLibAddin stack - QuantLib,
ObjectHandler, QuantLibAddin and the QuantLibXL Excel add-in (the `.xll` file) -
from a **git clone**, using the **cmake** build, in a **single** configure and
build from the repository root. It is the cmake counterpart of
[QuantLibXL/md/build_vs.md](QuantLibXL/md/build_vs.md) (the hand-maintained
Visual Studio solution build, which also builds the whole stack); both use the
same source files and produce the same XLL.

There are two ways to build the cmake projects in this repository:

1. **Each subproject on its own** - build the prerequisites first, then build
   one subproject against them. Use this when you want to build or test just one
   layer. See the per-subproject HOWTOs:
   [ObjectHandler](ObjectHandler/md/build_cmake.md),
   [QuantLibAddin](QuantLibAddin/md/build_cmake.md),
   [QuantLibXL](QuantLibXL/md/build_cmake.md).
2. **The whole stack from the repository root** (this document) - a single
   configure builds QuantLib, ObjectHandler, QuantLibAddin and QuantLibXL
   together. This is the simplest path if your goal is the QuantLibXL XLL: one
   clone, one configure, one build, no wiring between subprojects.

> **The two builds are independent.** The root build compiles every project from
> source into a single build tree at the repository root (`build\<preset>\`); it
> does **not** reuse - and is not affected by - the `build\<preset>\` directories
> that the per-subproject (standalone) builds create inside each subproject
> folder. The two live in separate directories and never share object or library
> files. Pick one path; you do not need both.

For other options:

- To download a compiled QuantLibXL XLL, see
  <https://www.quantlib.org/quantlibxl/installation.html>.
- To compile various flavors of QuantLibAddin (including the QuantLibXL XLL) from
  an official release of source code (zip files / tarballs), see
  <https://www.quantlib.org/quantlibaddin/tutorials.html>.

---

## 1 What gets built

The root build compiles the whole dependency chain
(`gensrc <- ObjectHandler <- QuantLibAddin <- QuantLibXL`, with QuantLib
supplying the analytics) in one pass. The headline output is the **QuantLibXL
Excel add-in**, a Windows DLL with an `.xll` extension; the build also produces
the intermediate libraries and the C++ demo client along the way:

| Target | Kind | Description |
|---|---|---|
| `QuantLib` (`ql_library`) | static library | the QuantLib analytics library |
| `xlsdk`, `ohlib`, `ohxllib` | static libraries | the ObjectHandler layers (`ohxllib` / `xlsdk` are Windows/Excel only) |
| `QuantLibObjects`, `AddinCpp` | static libraries | the QuantLibAddin wrapper and C++ add-in layers |
| `QLADemo` | executable | the QuantLibAddin C++ demo client |
| `QuantLibXL` | shared library (`.xll`) | the QuantLibXL Excel add-in |

The XLL is **Windows-only**. Building the `QuantLibXL` target builds everything
it depends on - QuantLib, the ObjectHandler static libraries and the
QuantLibAddin wrapper - in dependency order, so it is the simplest single target
to build (section 6).

### Platform support - Windows and Linux

The root cmake build runs on **Windows** and **Linux** (including **WSL**, which
is a Linux environment). The two platforms differ only in what the top layer
produces:

- **Windows** builds the whole chain including the **QuantLibXL** Excel add-in
  (the `.xll`) and the `QLADemo` C++ demo client.
- **Linux** builds QuantLib, the portable ObjectHandler / QuantLibAddin layers
  and the `QLADemo` C++ demo client. The Excel-only targets (`QuantLibXL`,
  `ohxllib`, `xlsdk`) are skipped because the XLL is Windows-only.

The sections below are written around the Windows presets; the **Linux/WSL**
specifics are called out inline - Boost in sections 3.2 and 5.1, the `linux-gcc`
preset in sections 6.1 and 7.1, and the output in section 8.

## 2 Choose a build - Basic or Full

Both builds produce the same artifacts; they differ only in whether the
auto-generated source code is regenerated. The choice is a single cmake cache
variable, `RUN_GENSRC`, set at configure time.

| Build | Configure with | Description |
|---|---|---|
| Basic | (default - `RUN_GENSRC` is `OFF`) | Compiles the auto-generated source files that are already present in the clone. Does **not** require Python. Use this for normal compilation. |
| Full  | `-DRUN_GENSRC=ON` | Runs gensrc first to (re)generate all auto-generated source files, then compiles. Requires Python 3. Use this on a fresh clone, or after you have changed the gensrc metadata (the XML files under `ObjectHandler\gensrc\metadata` or `QuantLibAddin\gensrc\metadata`). |

On a **fresh clone the first build must be a Full build** (`-DRUN_GENSRC=ON`)
because many sources are autogenerated and are not committed to the repository,
so on a pristine clone they do not exist yet. Otherwise cmake fails at configure
time with `Cannot find source file` for one of them (see section 10).

The advantage of the root build is that a **single** `-DRUN_GENSRC=ON` configure
generates **all** the autogenerated sources for the whole stack at once - the
ObjectHandler Excel sources, the QuantLibAddin `qlo` / `Addins\Cpp` sources, and
the QuantLibXL `qlxl` sources - so you do not run gensrc per subproject. After
one Full build the generated files exist, and subsequent Basic builds compile
them without needing Python.

## 3 Prerequisites

### 3.1 CMake and a C++ compiler

- **CMake 3.15 or later.** CMake ships with the **"C++ CMake tools for
  Windows"** component of the Visual Studio **"Desktop development with C++"**
  workload, so if you installed that workload you already have it. Check with
  `cmake --version`.
- **Visual Studio 2026 or 2022** with the **"Desktop development with C++"**
  workload. The cmake build is **x64 only**.
- **Linux (including WSL):** a C++17 compiler - **gcc/g++** (tested with gcc 11)
  - and CMake 3.15 or later. The `linux-gcc` preset uses the **Unix Makefiles**
  generator. WSL is a Linux environment, so the Windows presets above do not
  apply to it; use `linux-gcc` instead (section 6.1).

The platform toolset is selected automatically by the generator named in the
preset you choose (section 6); no manual toolset configuration is required:

| Visual Studio | Generator (from the preset) | Platform toolset |
|---|---|---|
| VS 2022 (v17) | `Visual Studio 17 2022` | v143 |
| VS 2026 (v18) | `Visual Studio 18 2026` | v145 |

On Linux there is no MSVC toolset tag: the generator is `Unix Makefiles` and the
compiler is gcc.

### 3.2 Boost

Every project in the stack depends on Boost. You need the **compiled** Boost
libraries, not just the headers (the build links the Boost `filesystem` and
`serialization` components). Building Boost is outside the scope of this
document; these instructions assume you already have a Boost build available.

The build requires **Boost 1.58 or later**. It was tested using **Boost 1.83**.

For purposes of this HOWTO, it is assumed that you have installed Boost to:

```
C:\repos\boost_1_83_0
```

with headers under `C:\repos\boost_1_83_0` (i.e. the folder that contains the
`boost\` sub-directory) and the compiled libraries under
`C:\repos\boost_1_83_0\stage\lib`. Modify that path as necessary for your own
environment.

The root cmake build has a **single** Boost configuration point: you supply the
include and library directories once, in `CMakeUserPresets.json` (section 5),
and cmake applies them to every project in the build (QuantLib included).

**On Linux** the shared `linux-gcc` preset instead expects Boost to be found
automatically by `find_package` - typically the distribution packages
(`libboost-filesystem-dev`, `libboost-serialization-dev`) or a vcpkg / conan
install. If you point at a hand-built Boost (for example under WSL, where you
may have compiled only `filesystem` and `serialization` from source), supply the
same `BOOST_*` variables in a Linux user preset (section 5.1).

### 3.3 Python 3 (Full build only)

The **Full** build (`-DRUN_GENSRC=ON`) runs gensrc, which is a Python 3 script.
Install Python 3 and make sure `python` is on the `PATH` (i.e. `python
--version` works from a command prompt). See <https://www.python.org/>. When
`RUN_GENSRC` is on, cmake locates the interpreter itself via `find_package`.

The **Basic** build does not use Python or gensrc, so you can skip this section
for a Basic build.

## 4 Acquire the source code

The build refers to the prerequisite projects using **relative paths**, so the
directory layout matters. After cloning you must end up with this layout (the
outer `QuantLibAddin` folder is the repository root - you may name it anything
you like; it is where `CMakeLists.txt`, `CMakePresets.json` and this
`build_cmake.md` live):

```
QuantLibAddin\         (the repository root - the outer folder)
  gensrc\
  ObjectHandler\
  QuantLib\            (cloned separately - see below)
  QuantLibAddin\
  QuantLibXL\
```

### 4.1 Clone the main repository

`gensrc`, `ObjectHandler`, `QuantLibAddin` and `QuantLibXL` are all contained in
this single repository. Clone it:

```
git clone <repo-host>/<owner>/QuantLibAddIn.git
```

This creates the `QuantLibAddin` folder containing the four sub-projects above.

### 4.2 Clone QuantLib into the working tree

QuantLib is maintained as a **separate** repository and is deliberately excluded
from this one (it is listed in `.gitignore`), so the root build expects you to
clone it yourself into a sub-folder named exactly `QuantLib` inside the working
tree you just cloned:

```
cd QuantLibAddin
git clone <repo-host>/<owner>/QuantLib QuantLib
```

The folder name `QuantLib` **is case sensitive** and must be spelled exactly as
shown - `QuantLib`, not `quantlib` or `QUANTLIB`, and with no version suffix -
because the root `CMakeLists.txt` adds the sub-directory by that name with
`add_subdirectory(QuantLib)`. The explicit `QuantLib` argument at the end of the
`git clone` command ensures the folder is named `QuantLib` (without it git would
create a folder whose name matches the source repository, for example
`quantlib`, or another name if you are cloning a fork).

After this step the layout in section 4 should be in place.

## 5 Configure Boost (required)

Boost paths are **not** baked into the shared `CMakePresets.json`. Instead each
user supplies them in a `CMakeUserPresets.json` file in the repository root
(next to `CMakePresets.json`). That file is listed in `.gitignore` and is never
committed, so your local paths stay out of the repository.

`CMakePresets.json` defines hidden **base** presets (compiler, architecture and
runtime selection); your `CMakeUserPresets.json` defines the presets you
actually use, each **inheriting** a base preset and adding your Boost paths.
Create it by copying the template below and adjusting the two Boost paths:

```json
{
    "version": 6,
    "configurePresets": [
        {
            "name": "windows-vs2026-x64-static",
            "displayName": "VS 2026 x64 - static CRT",
            "inherits": "windows-vs2026-x64-static-base",
            "cacheVariables": {
                "BOOST_INCLUDEDIR": "C:/repos/boost_1_83_0",
                "BOOST_LIBRARYDIR": "C:/repos/boost_1_83_0/stage/lib"
            }
        },
        {
            "name": "windows-vs2026-x64-dynamic",
            "displayName": "VS 2026 x64 - dynamic CRT",
            "inherits": "windows-vs2026-x64-dynamic-base",
            "cacheVariables": {
                "BOOST_INCLUDEDIR": "C:/repos/boost_1_83_0",
                "BOOST_LIBRARYDIR": "C:/repos/boost_1_83_0/stage/lib"
            }
        },
        {
            "name": "windows-vs2022-x64-static",
            "displayName": "VS 2022 x64 - static CRT",
            "inherits": "windows-vs2022-x64-static-base",
            "cacheVariables": {
                "BOOST_INCLUDEDIR": "C:/repos/boost_1_83_0",
                "BOOST_LIBRARYDIR": "C:/repos/boost_1_83_0/stage/lib"
            }
        },
        {
            "name": "windows-vs2022-x64-dynamic",
            "displayName": "VS 2022 x64 - dynamic CRT",
            "inherits": "windows-vs2022-x64-dynamic-base",
            "cacheVariables": {
                "BOOST_INCLUDEDIR": "C:/repos/boost_1_83_0",
                "BOOST_LIBRARYDIR": "C:/repos/boost_1_83_0/stage/lib"
            }
        }
    ],
    "buildPresets": [
        { "name": "windows-vs2026-x64-static-release",  "configurePreset": "windows-vs2026-x64-static",  "configuration": "Release" },
        { "name": "windows-vs2026-x64-static-debug",    "configurePreset": "windows-vs2026-x64-static",  "configuration": "Debug"   },
        { "name": "windows-vs2026-x64-dynamic-release", "configurePreset": "windows-vs2026-x64-dynamic", "configuration": "Release" },
        { "name": "windows-vs2026-x64-dynamic-debug",   "configurePreset": "windows-vs2026-x64-dynamic", "configuration": "Debug"   },
        { "name": "windows-vs2022-x64-static-release",  "configurePreset": "windows-vs2022-x64-static",  "configuration": "Release" },
        { "name": "windows-vs2022-x64-static-debug",    "configurePreset": "windows-vs2022-x64-static",  "configuration": "Debug"   },
        { "name": "windows-vs2022-x64-dynamic-release", "configurePreset": "windows-vs2022-x64-dynamic", "configuration": "Release" },
        { "name": "windows-vs2022-x64-dynamic-debug",   "configurePreset": "windows-vs2022-x64-dynamic", "configuration": "Debug"   }
    ]
}
```

Notes:

- `BOOST_INCLUDEDIR` is the directory that **contains** the `boost\` header
  sub-folder (so that `#include <boost/config.hpp>` resolves).
- `BOOST_LIBRARYDIR` is the directory that contains the compiled `.lib` files.
  Boost auto-linking is disabled in this build, so cmake selects the correct
  libraries (`filesystem` and `serialization`) from that directory; you do not
  list individual libraries.
- Paths in JSON use **forward slashes** (or escaped `\\`). The `static` presets
  request the static-runtime Boost libraries (`/MT`) and the `dynamic` presets
  the dynamic-runtime ones (`/MD`); this **must** match the runtime of the Boost
  libraries you point at (see the `LNK2038` note in section 10).
- You only need the presets you intend to use - delete the others from your
  `CMakeUserPresets.json` if you build with just one compiler.

If Boost is installed somewhere cmake can find automatically (for example via a
`BOOST_ROOT` environment variable or vcpkg), `CMakeUserPresets.json` can be
omitted entirely and the shared presets will work as-is.

### 5.1 Linux / WSL preset (optional)

The shared `CMakePresets.json` already defines a ready-to-use **`linux-gcc`**
configure preset (Unix Makefiles + gcc + C++17) that finds Boost via
`find_package`. On a distro where Boost is installed system-wide you need
nothing more - skip to section 6.1 and use `--preset linux-gcc`.

If your Boost is not on the default search path (the usual case under **WSL**
with a hand-built Boost), add a Linux preset to `CMakeUserPresets.json` that
**inherits** `linux-gcc` and supplies the paths, exactly as the Windows presets
inherit their bases:

```json
{
    "name": "linux-gcc-wsl",
    "displayName": "Linux GCC (WSL, local Boost)",
    "inherits": "linux-gcc",
    "cacheVariables": {
        "BOOST_ROOT": "/home/you/boost_1_83_0",
        "BOOST_INCLUDEDIR": "/home/you/boost_1_83_0",
        "BOOST_LIBRARYDIR": "/home/you/boostlibs/lib",
        "Boost_NO_SYSTEM_PATHS": true,
        "Boost_USE_STATIC_LIBS": true
    }
}
```

and a matching **build** preset in the same file:

```json
{ "name": "linux-gcc-wsl", "configurePreset": "linux-gcc-wsl" }
```

(`Unix Makefiles` is single-config, so the Linux build preset takes **no**
`configuration` field - unlike the Windows build presets above. The build type
is fixed at configure time by `CMAKE_BUILD_TYPE`, which the `linux-gcc` base
preset sets to `Release`.)

## 6 Configure

Open a **Developer PowerShell / Command Prompt** (or any shell where `cmake` is
on the `PATH`), change to the **repository root** - the outer `QuantLibAddin`
folder that contains `CMakePresets.json` - and run cmake with the preset you
want. Unlike a standalone subproject build, the root build needs **no**
`CMAKE_PREFIX_PATH`: every project is part of the same configure, so there are no
prebuilt prerequisites to locate. The preset's `binaryDir` puts the build under
`build\<preset>\` automatically.

On a **fresh clone**, or whenever you want to (re)generate the autogenerated
sources, add `-DRUN_GENSRC=ON` to configure a **Full** build, which runs gensrc
for the whole stack first (this requires Python 3 - see section 3.3):

```powershell
# VS 2026, static CRT  (recommended for distribution)
cmake --preset windows-vs2026-x64-static -DRUN_GENSRC=ON

# VS 2026, dynamic CRT
cmake --preset windows-vs2026-x64-dynamic -DRUN_GENSRC=ON

# VS 2022, static CRT
cmake --preset windows-vs2022-x64-static -DRUN_GENSRC=ON

# VS 2022, dynamic CRT
cmake --preset windows-vs2022-x64-dynamic -DRUN_GENSRC=ON
```

gensrc runs once, during this configure step, and writes the generated sources
into the source tree.

Once the autogenerated sources exist, drop `-DRUN_GENSRC=ON` to configure a
**Basic** build (section 2) - the default - which skips gensrc:

```powershell
cmake --preset windows-vs2026-x64-static
```

After a successful configure you can build (section 7); unless you change the
gensrc metadata, you only need a Full configure once.

### 6.1 Configure on Linux / WSL

Use the `linux-gcc` preset (or your `linux-gcc`-derived user preset from section
5.1). `RUN_GENSRC` behaves exactly the same way as on Windows:

```bash
# system Boost
cmake --preset linux-gcc -DRUN_GENSRC=ON

# hand-built Boost (the WSL user preset from section 5.1)
cmake --preset linux-gcc-wsl -DRUN_GENSRC=ON
```

The Windows presets carry a `condition` that enables them only when
`hostSystemName == Windows`, so under WSL they are reported as **disabled**
(see section 10) - they use a Visual Studio generator that does not exist on
Linux. Use `linux-gcc` instead.

## 7 Build

The Visual Studio generator is multi-config, so the **same** build directory
produces either Release or Debug. The simplest way to build is with a **build
preset**, which selects the configuration for you and writes to the configure
preset's `build\<preset>\` directory:

```powershell
# Release  (build preset names end in -release / -debug)
cmake --build --preset windows-vs2026-x64-static-release --target QuantLibXL

# Debug
cmake --build --preset windows-vs2026-x64-static-debug --target QuantLibXL
```

Equivalently, point `cmake --build` at the preset's build directory and choose
the configuration with `--config`:

```powershell
# Release static  ->  QuantLibXL-v145-x64-mt-s-1_42_0.xll
cmake --build build\windows-vs2026-x64-static --config Release --target QuantLibXL

# Debug static    ->  QuantLibXL-v145-x64-mt-sgd-1_42_0.xll
cmake --build build\windows-vs2026-x64-static --config Debug   --target QuantLibXL
```

The `--target QuantLibXL` argument builds the XLL and everything it depends on
(QuantLib, the ObjectHandler static libraries and the QuantLibAddin libraries)
in dependency order. Omit `--target` to build the default target set, which also
includes the `QLADemo` C++ demo client.

For the VS 2022 presets the toolset tag in the output name is `v143` instead of
`v145`; for the dynamic presets the runtime tag is `-mt` / `-mt-gd` instead of
`-mt-s` / `-mt-sgd` (see section 8).

### 7.1 Build on Linux / WSL

The `linux-gcc` generator (Unix Makefiles) is single-config, so the
configuration is fixed at configure time (`Release` by default). Build with the
build preset:

```bash
cmake --build --preset linux-gcc --target QLADemo
```

**Limit parallelism on memory-constrained machines.** QuantLib's template-heavy
translation units each need a lot of RAM; a bare `-j` (unlimited jobs) can
exhaust memory - common under WSL, whose VM has a capped RAM / swap budget - and
the Linux OOM killer then terminates the compiler with
`g++: fatal error: Killed signal terminated program cc1plus`. Pass an explicit,
modest job count instead (roughly one job per ~2 GB of RAM):

```bash
cmake --build --preset linux-gcc --target QLADemo -j 2
```

See section 10 for the OOM symptom and `.wslconfig` tuning.

## 8 Output

On success the add-in is written to `build\<preset>\xll\`. This is **separate**
from the Visual Studio build's output (`QuantLibXL\xll\`), so the two builds do
not overwrite each other. The file name encodes the platform toolset, the
platform, the runtime variant and the version:

| Preset | Config | Output file (under `build\<preset>\xll\`) |
|---|---|---|
| `windows-vs2026-x64-static`  | Release | `QuantLibXL-v145-x64-mt-s-1_42_0.xll` |
| `windows-vs2026-x64-static`  | Debug   | `QuantLibXL-v145-x64-mt-sgd-1_42_0.xll` |
| `windows-vs2026-x64-dynamic` | Release | `QuantLibXL-v145-x64-mt-1_42_0.xll` |
| `windows-vs2026-x64-dynamic` | Debug   | `QuantLibXL-v145-x64-mt-gd-1_42_0.xll` |
| `windows-vs2022-x64-static`  | Release | `QuantLibXL-v143-x64-mt-s-1_42_0.xll` |
| `windows-vs2022-x64-static`  | Debug   | `QuantLibXL-v143-x64-mt-sgd-1_42_0.xll` |
| `windows-vs2022-x64-dynamic` | Release | `QuantLibXL-v143-x64-mt-1_42_0.xll` |
| `windows-vs2022-x64-dynamic` | Debug   | `QuantLibXL-v143-x64-mt-gd-1_42_0.xll` |

The C++ demo client `QLADemo` (built when you omit `--target`) is written
alongside, under `build\<preset>\cpp\`, with the same toolset/runtime tags.

The static-runtime (`-mt-s` / `-mt-sgd`) XLL is self-contained and does not
require the Visual C++ runtime to be installed on the target machine, which is
usually what you want for distribution.

**On Linux** there is no XLL. The build produces the `QLADemo` C++ demo client
under `build/<preset>/cpp/`. With gcc there is no MSVC toolset tag, so the name
has no `v143` / `v145` segment - for example `QLADemo-x64-mt-1_42_0` (an ELF
executable, with no file extension).

## 9 Build the documentation (optional)

Each project (gensrc, ObjectHandler, QuantLibAddin, QuantLibXL) ships a Doxygen
documentation build. It is **off by default** and gated by the configure-time
cmake option `BUILD_DOCS` (default `OFF`), so a normal build adds no doc targets
- which is why `cmake --build ... --target docs` fails with
`No rule to make target 'docs'` until you enable it.

The documentation is independent of the Basic/Full (`RUN_GENSRC`) choice and
needs **no C++ compiler or Boost** - only Python 3 and Doxygen (and optionally
Graphviz). It works on **Windows and Linux/WSL** alike (the `QuantLibXL` docs
build everywhere, even though the XLL itself is Windows-only).

### 9.1 Enable the doc targets

`BUILD_DOCS` is read at **configure** time, so you must re-run cmake with it set
before the doc targets exist (`--build` alone cannot add them). Re-configure the
same preset you already use, adding `-DBUILD_DOCS=ON`:

```powershell
# Windows
cmake --preset windows-vs2026-x64-static -DBUILD_DOCS=ON
```

```bash
# Linux / WSL
cmake --preset linux-gcc -DBUILD_DOCS=ON
```

### 9.2 Build

The integrated build adds an aggregate `docs` target plus one target per
project. Build them all, or just the one you want:

```powershell
# Windows - everything
cmake --build --preset windows-vs2026-x64-static-release --target docs

# Windows - one project
cmake --build --preset windows-vs2026-x64-static-release --target gensrc-docs
```

```bash
# Linux / WSL - everything
cmake --build --preset linux-gcc --target docs

# Linux / WSL - one project
cmake --build --preset linux-gcc --target gensrc-docs
```

| Target | Builds |
|---|---|
| `docs` | all four projects (aggregate) |
| `gensrc-docs` | gensrc only |
| `ObjectHandler-docs` | ObjectHandler only |
| `QuantLibAddin-docs` | QuantLibAddin only |
| `QuantLibXL-docs` | QuantLibXL only (builds on any platform) |

### 9.3 Tools (Doxygen / Graphviz on PATH)

The doc tools are discovered **at configure time** (the step in section 9.1),
not when you build:

- **Python 3** and **Doxygen** are **required**. If `doxygen` is not on `PATH`,
  the `-DBUILD_DOCS=ON` configure **fails** with
  `doxygen was not found on PATH; cannot build the documentation`.
- **Graphviz `dot`** is **optional**. If present it enables the inheritance /
  collaboration diagrams; if absent, configure prints
  `dot (Graphviz) not found; diagrams will be skipped` and continues.

So install Doxygen (and optionally Graphviz) and make sure they are on `PATH`
*before* you re-configure.

### 9.4 Output

The HTML is written under the build tree (the source tree stays clean), one
folder per target:

```
build/<preset>/<target>/html/index.html
```

for example `build/<preset>/gensrc-docs/html/index.html`. Open `index.html` in a
browser to read the generated documentation.

## 10 Troubleshooting

**CMake error: `add_subdirectory given source "QuantLib" which is not an
existing directory`** (or `Cannot find source file` for QuantLib sources) at
configure time. The `QuantLib` folder is missing or misnamed. Clone it as
described in section 4.2 - remember the name is case sensitive.

**CMake error: `Cannot find source file`** for one of the `qlo\valueobjects\*`,
`qlo\serialization\**`, `Addins\Cpp\*`, `ohxl\**` or `qlxl\**` files at configure
time. The autogenerated sources are not present - this is a **fresh clone** and
you ran a Basic build. Configure a **Full** build once with `-DRUN_GENSRC=ON`
(sections 2 and 6) to generate them; this needs Python 3.

**CMake error: `Could NOT find Boost`** at configure time. `BOOST_INCLUDEDIR`
or `BOOST_LIBRARYDIR` is missing or wrong in your `CMakeUserPresets.json`, or
your Boost build is missing the `filesystem` / `serialization` components.
Re-check section 5: `BOOST_INCLUDEDIR` must point at the folder that contains
the `boost\` sub-directory, and `BOOST_LIBRARYDIR` at the folder that contains
the compiled `.lib` files.

**CMake error: `No such preset in ...` / `Could not read presets`** when you run
`cmake --preset`. Either you are not in the repository root (run cmake from the
outer `QuantLibAddin` folder that contains `CMakePresets.json`), or the preset
name is not defined in your `CMakeUserPresets.json`. Check section 5.

**CMake error: `Could not use disabled preset "windows-..."`** when you run
`cmake --preset` under **Linux / WSL**. The `windows-*` presets carry a
`condition` that enables them only when `hostSystemName == Windows`, so on Linux
(and WSL is Linux) they are disabled, and they use a Visual Studio generator
that does not exist there anyway. Use the `linux-gcc` preset - or a
`linux-gcc`-derived user preset - instead (sections 5.1 and 6.1).

**`error C1083: Cannot open include file: 'boost/config.hpp'`** during
compilation. `BOOST_INCLUDEDIR` does not point at the directory that contains
the `boost\` header sub-folder. Fix it in `CMakeUserPresets.json` and
re-configure.

**`error LNK1104: cannot open file 'libboost_...lib'`** at the link stage. The
Boost library directory is wrong, or the static/dynamic runtime variant your
preset asked for is not present in `BOOST_LIBRARYDIR`. Make sure
`BOOST_LIBRARYDIR` points at a Boost build that provides the matching runtime
libraries for the preset you chose, then re-configure.

**`error LNK2038: mismatch detected for 'RuntimeLibrary'`** (for example
`value 'MT_StaticRelease' doesn't match value 'MD_DynamicRelease'`), usually
followed by `error LNK1169: one or more multiply defined symbols found`, at the
link stage. Your Boost libraries were built against a different C runtime than
the preset selected. The `dynamic` presets compile `/MD` (dynamic CRT); the
`static` presets compile `/MT` (static CRT), and the Boost `.lib` files in
`BOOST_LIBRARYDIR` must match. Use the preset whose CRT matches your Boost
libraries, or build the missing Boost runtime variant, then re-configure.

(The Boost `bind.hpp` "declaring the Bind placeholders ... is deprecated" lines
that may appear earlier in the log are harmless deprecation *messages*, not the
cause of this failure.)

**Linux / WSL build aborts with `g++: fatal error: Killed signal terminated
program cc1plus`** (followed by `compilation terminated.`). This is the Linux
**OOM (out-of-memory) killer**, not a code error: the kernel sent `SIGKILL` to
the compiler because the machine ran out of RAM. A tell-tale sign is that
re-running the build resumes *past* the file that failed (completed object files
are kept) and stops on a *different* file each time. It is usually triggered by
an unbounded `-j` (unlimited parallel compiles), each of which can use 1-2 GB on
QuantLib's heavy templates. Fixes: pass a modest job count (`-j 2`), and / or
raise the WSL memory and swap limits in `C:\Users\<you>\.wslconfig` on the
Windows side:

```ini
[wsl2]
memory=12GB
swap=16GB
```

then run `wsl --shutdown` from Windows PowerShell to apply it. See section 7.1.

**Python errors during a Full build**, or you expected regeneration but the
generated files were not refreshed. gensrc only runs when you configure with
`-DRUN_GENSRC=ON` (section 6); install Python 3 and ensure `python --version`
works.

**`No rule to make target 'docs'`** (or `gmake: *** No rule to make target
'docs'. Stop.`) when you run `cmake --build ... --target docs`. The doc targets
are gated by the `BUILD_DOCS` option, which is `OFF` by default, so they do not
exist in the current build tree. Re-configure the preset with `-DBUILD_DOCS=ON`
first (section 9.1); this is a configure-time option, so `--build` alone cannot
add the target.

**`doxygen was not found on PATH; cannot build the documentation`** at configure
time, after you added `-DBUILD_DOCS=ON`. Doxygen is required to build the docs
and must be on `PATH` when cmake configures. Install Doxygen (and optionally
Graphviz `dot` for diagrams), make sure `doxygen --version` works in the same
shell, then re-configure (section 9.3).

## 11 Load the add-in in Excel

1. Open Excel.
2. Go to **File > Options > Add-ins**.
3. Set **Manage** to **Excel Add-ins** and click **Go**.
4. Click **Browse**, navigate to the `.xll` produced in section 8 (under
   `build\<preset>\xll\`), and click **OK**.

Alternatively, drag and drop the `.xll` onto an open Excel window.

## 12 Load a sample workbook

With the add-in loaded, open one of the sample workbooks to confirm the
functions are available and to see the add-in in action. The best ones to start
with are:

```
QuantLibXL\StandaloneExamples\Analytics\YieldCurveBootstrapping.xlsx
QuantLibXL\StandaloneExamples\Analytics\InterestRateDerivatives.xlsx
```

Open one of these workbooks in the same Excel instance that has the add-in
loaded, then recalculate (`Ctrl+Alt+F9`) to evaluate the QuantLib functions. If
the functions evaluate without `#NAME?` errors, the build is good.
